# Deployment Guide

Practical build and deployment steps for the GlobalTrade SCM platform. See
[`docs/CRITICAL_ANALYSIS.md`](./CRITICAL_ANALYSIS.md) for the architectural
rationale behind the decisions referenced here.

## Prerequisites

| Tool | Version | Notes |
|---|---|---|
| JDK | 17+ | `maven.compiler.release=17` in the parent POM. |
| Maven | 3.9+ | Needs network access to Maven Central to resolve `jakarta.jakartaee-api`, `mysql-connector-j`, JUnit, Mockito and Arquillian — not available in every sandboxed build environment; a normal developer machine or CI runner with outbound internet access is assumed. |
| GlassFish | 7.x (Jakarta EE 10) | Matches the `jakarta.*` namespace used throughout `scm-ejb`/`scm-web`. |
| MySQL | 8.0+ | `utf8mb4`/`utf8mb4_0900_ai_ci`, InnoDB — see `db/schema.sql`. |

This project was developed and its source verified for correct Java syntax with
`javac 21`, but **could not be built end-to-end with Maven or deployed to a live
GlassFish instance in the environment it was written in**, because that
environment's network access is restricted to a small allow-list of domains that
does not include Maven Central or an Eclipse GlassFish download mirror. Every file
was written and cross-checked by hand against the actual field names, method
signatures, and constructors already present in the codebase (see the extensive
verification steps throughout this project's development), and the full source
tree was compiled together with `javac` to confirm there are no syntax errors —
but a real `mvn verify` and a real GlassFish deployment have not been executed
against this exact tree. Budget time for the normal first-deployment debugging
cycle (dependency version conflicts, GlassFish-version-specific descriptor syntax —
several files carry an explicit comment flagging this — and environment-specific
configuration) that any new Java EE project goes through.

## 1. Database setup

```bash
mysql -u root -p < db/schema.sql
```

This creates the `globaltrade_scm` database, all nine tables, and seed data
including six demo user accounts (one per role) with **real, working** PBKDF2
password hashes generated by the actual `SecurityUtil` algorithm — see the header
comment in `db/schema.sql` for the username/password/role table. Change every one
of these credentials before deploying beyond a local/demo environment.

## 2. GlassFish: JDBC resource

Edit `deploy/glassfish-resources.xml`, replacing the `${MYSQL_HOST}`,
`${MYSQL_PORT}`, `${MYSQL_USER}`, `${MYSQL_PASSWORD}` placeholders with real
values (or resolve them with `envsubst` if you prefer to keep the file
parameterized in version control):

```bash
export MYSQL_HOST=localhost MYSQL_PORT=3306 MYSQL_USER=scm_app MYSQL_PASSWORD='change-me'
envsubst < deploy/glassfish-resources.xml > /tmp/glassfish-resources-resolved.xml
asadmin start-domain
asadmin add-resources /tmp/glassfish-resources-resolved.xml
```

Verify: `asadmin list-jdbc-resources` should show `jdbc/SCMDataSource`, and
`asadmin ping-connection-pool SCMConnectionPool` should succeed. The MySQL JDBC
driver (`mysql-connector-j`) needs to be on GlassFish's own classpath for this pool
to work — copy the jar (matching the version pinned in the parent POM) into
`${glassfish.home}/glassfish/domains/domain1/lib/ext/` and restart the domain if
`ping-connection-pool` reports a missing driver class.

## 3. GlassFish: custom JAAS realm

This is the one step in this guide most likely to need adjustment for your exact
GlassFish point release — GlassFish's realm/login-module wiring is one of its more
version-sensitive proprietary areas, unlike the portable `ejb-jar.xml`/`web.xml`
syntax used elsewhere in this project. What follows is the standard JAAS-level
configuration (very stable, high confidence) plus the GlassFish realm-registration
command pattern (verify the `--classname` value against your specific GlassFish
version's realm documentation before running it).

**3a. Register the login module with a named JAAS context.** Add an entry to
`${domain.dir}/config/login.conf`:

```
supplyChainRealm {
    com.globaltrade.scm.security.SupplyChainLoginModule required;
};
```

**3b. Register a custom auth realm bound to that context**, so
`web.xml`'s `<realm-name>supplyChainRealm</realm-name>` and this application's
remote-EJB security both resolve to it:

```bash
asadmin create-auth-realm \
    --classname com.sun.enterprise.security.ee.auth.realm.custom.CustomRealm \
    --property jaas-context=supplyChainRealm \
    supplyChainRealm
```

If `create-auth-realm` rejects that `--classname` on your GlassFish version, the
equivalent can be added directly to `${domain.dir}/config/domain.xml`'s
`<security-service>` element:

```xml
<auth-realm name="supplyChainRealm" classname="<verify-for-your-glassfish-version>">
    <property name="jaas-context" value="supplyChainRealm"/>
</auth-realm>
```

**3c. Make it the default realm** for the virtual server this application deploys
to (`asadmin set server-config.security-service.default-realm=supplyChainRealm`),
or configure a per-application realm override if you would rather leave the
domain's own default realm untouched.

`SupplyChainLoginModule` (see its own javadoc) is a portable, standard
`javax.security.auth.spi.LoginModule` with zero GlassFish-specific base-class
dependency — only *this realm-registration step*, not the login module's own code,
is GlassFish-specific.

## 4. Build

```bash
mvn -pl scm-common,scm-ejb,scm-web,scm-ear -am clean package
```

Produces `scm-ear/target/globaltrade-scm.ear`, plus `scm-ejb/target/scm-ejb-client.jar`
(the thin remote-client artifact — see
[`CRITICAL_ANALYSIS.md`, "Remote vs. local interface selection"](./CRITICAL_ANALYSIS.md#remote-vs-local-interface-selection-for-carrier-and-vendor-system-integration)).

## 5. Deploy

```bash
asadmin deploy --contextroot scm scm-ear/target/globaltrade-scm.ear
```

(`--contextroot scm` is belt-and-suspenders here — `scm-web`'s `glassfish-web.xml`
and `scm-ear`'s `application.xml` already agree on `/scm`.)

## 6. Smoke test

```bash
# Register a shipment (LOGISTICS_COORDINATOR or ADMIN)
curl -k -u jcoordinator:Coord@12345 -X POST https://localhost:8181/scm/api/shipments \
    -H 'Content-Type: application/json' \
    -d '{"trackingNumber":"GT-SMOKE-001","vendorId":1,"carrierId":1,
         "originCountry":"CN","destinationCountry":"SE","weightKg":120.5}'

# Track it (any authenticated role, including CUSTOMER)
curl -k -u customer1:Customer@12345 https://localhost:8181/scm/api/shipments/GT-SMOKE-001

# Place a full order through the BMT workflow (exercises inventory reservation +
# shipment registration + conditional customs clearance in one call)
curl -k -u jcoordinator:Coord@12345 -X POST https://localhost:8181/scm/api/orders \
    -H 'Content-Type: application/json' \
    -d '{"sku":"SKU-TEX-1001","quantity":10,"vendorId":1,"carrierId":3,
         "originCountry":"CN","destinationCountry":"SE"}'
```

Port `8181` assumes GlassFish's default HTTPS listener; adjust for your domain's
actual configuration. `-k` skips certificate verification for a local
self-signed cert — do not carry that flag into anything beyond local testing.

## 7. Running the tests

```bash
# Plain unit tests (security/, recovery/) -- no container needed
mvn -pl scm-ejb test

# Arquillian integration tests (it/) -- needs a running GlassFish with
# db/schema.sql already loaded and jdbc/SCMDataSource already configured
# (steps 1-3 above)
# First, edit scm-ejb/src/test/resources/arquillian.xml with your GlassFish
# admin host/port/credentials.
mvn -pl scm-ejb verify
```

`OrderProcessingWorkflowIT`'s test methods reference specific seed-data ids
(vendor 1/2, carrier 1/3, SKUs `SKU-TEX-1001`/`SKU-ELE-2002`) from `db/schema.sql`
— re-run `db/schema.sql` against a clean database before re-running the
integration tests if you have since mutated that seed data through the API.

## 8. Known limitations and environment-specific verification checklist

- [ ] `glassfish-ejb-jar.xml`, `glassfish-web.xml`, `glassfish-application.xml`:
      DOCTYPE/DTD versions target GlassFish 3.1-era descriptor syntax, which
      GlassFish has long maintained for backward compatibility, but confirm
      `asadmin deploy` does not reject them on your specific point release.
- [ ] Step 3 above (custom realm registration): verify the exact
      `create-auth-realm --classname` value for your GlassFish version.
- [ ] `scm-ejb/pom.xml`'s Arquillian GlassFish container-adapter coordinate
      (`arquillian-glassfish-remote-3.1:1.0.2`) is the piece of the dependency
      graph most likely to need a version bump — check Arquillian's current
      GlassFish-adapter compatibility matrix against your GlassFish version.
- [ ] `application.xml`'s schema version (`version="10"`, tracking the Jakarta EE
      10 platform version) and `ejb-jar.xml`'s (`version="4.0"`, tracking the EJB
      4.0 component spec independently) — confirm both against the exact GlassFish
      build in use if deployment fails with a descriptor-validation error.
- [ ] MySQL JDBC driver placement on GlassFish's classpath (end of Section 2).
- [ ] HTTPS listener configuration for the `CONFIDENTIAL` transport guarantee in
      `web.xml` to actually take effect — a fresh GlassFish domain's default
      HTTPS listener is usually already present (port 8181), but confirm before
      relying on it in a non-default domain configuration.
